# Phase 4 online Secret Bid

The round engine, PostgreSQL room store, authenticated Vercel API, private Pusher adapter, voting, and browser lobby are implemented. API integration and the complete two-browser match pass against embedded PostgreSQL. Live provider verification remains pending.

## Architecture decision

Use Vercel Node.js functions for the same-origin API, Neon Postgres for authoritative room state, and Pusher Channels for private room update notifications. The existing Vite app and local mode stay independent of all three services. Deploy the local MVP as the baseline before enabling online rooms in production.

Vercel Functions have WebSocket support in public beta, with connections tied to the lifetime of a function instance. A managed connection service lets the API remain stateless and leaves cross-instance consistency to Postgres. [Vercel WebSocket support](https://vercel.com/changelog/websocket-support-is-now-in-public-beta)

Use a Vercel project, a Neon database and a Pusher Channels app. The online API requires server-side `DATABASE_URL`, `ONLINE_SESSION_PEPPER`, and `ONLINE_ORIGIN`. Private realtime connections use `PUSHER_APP_ID`, `PUSHER_KEY`, `PUSHER_SECRET`, and `PUSHER_CLUSTER` together. The bootstrap returns only the intentionally public Pusher key and cluster. An authenticated cleanup job uses `CRON_SECRET`. Use separate databases, Pusher apps, and secrets for production and restricted previews. Local Secret Bid runs with no environment variables.

## Room and request security

- The server creates an opaque public room ID, a high-entropy guest session, and a single-use invite for the second seat. It stores keyed digests of the session and invite secrets. The client moves the invite secret from the URL fragment into the current browser history entry so a refresh can resume joining. It clears that state when the guest joins or resumes a seat. The server consumes the invite atomically when the second seat is assigned. Unused invites expire after 30 minutes. Hosts can revoke and rotate an unused invite.
- Keep the guest session in a host-only `HttpOnly`, `Secure`, `SameSite=Lax` cookie. Every room request checks recent session validity and its assigned seat. Only the host starts a full lobby. Players can submit for their own seat. Either player can advance a resolved round so a disconnect cannot leave the other player stranded. Mutations require the expected same-origin `Origin` and a bounded JSON body. Refresh keeps the seat while the cookie and room remain valid.
- Server snapshots explicitly allowlist fields. They include the current item, visible roster and budgets, deadline, public revision and revealed outcome, plus the viewer’s own eligibility and lock status. The deck order, upcoming items, pending bids and the opponent’s lock status stay server-side. Resolve a round and expose both bids in one committed update. Use `Cache-Control: no-store` on room, invite and authorization responses. Keep raw bodies, cookies, invite fragments and bids out of logs.
- Authorize Pusher subscriptions only to the exact private channel for the caller’s room. Enable authorized connections and leave client events disabled. The server publishes a `{ revision }` hint after a public commit. Every hint triggers an authenticated HTTP snapshot. Invalidations contain no names, bids, cards, results or credentials. [Pusher authorized connections](https://pusher.com/docs/channels/using_channels/authorized-connections/)
- Start with persisted limits for creation, invite redemption, auth and mutations. Key limits by session and by a short-lived keyed digest of the platform-provided client IP. Bound active rooms and lobby churn, return `429` with retry guidance, and cap polling frequency. Use generic responses for invalid room codes and invite tokens. Keep spectator access out of the initial release. Restrict voting to the two room seats, one ballot per seat, and close voting 15 minutes after finishing.

## State and ordering

- Server-side room creation draws cards with cryptographic randomness. The online flow opens both eligible seats simultaneously for 15 seconds. It feeds the same budget, tie, discard and mandatory-assignment logic as local play. A full seat has no bid. If time runs out, every eligible seat without a locked bid passes for $0. The database clock decides the deadline after taking the room lock, so a request that reaches the transaction after the deadline cannot replace the pass.
- In one Postgres transaction, lock the room row with `SELECT … FOR UPDATE`, authorize the seat, check expiry, and re-read the current round and revision. Store one accepted bid per seat per round and never charge until resolution. A private lock leaves the public revision unchanged, so either player can submit against the same round. Resolve once when both eligible bids are present or the deadline arrives. Public transitions increment the revision and stale public actions return the latest authorized snapshot. Scope request IDs to the room and seat, reject reuse with different payloads, and return the authorized snapshot on a retry of the same request.
- On reconnect, attach the private subscription and request the current snapshot, then re-fetch on notification and after gaps. Apply snapshots in revision order. Serialize snapshot requests per tab and preserve its own locked status on identical revisions. Visible clients poll every two seconds as a fallback when realtime is unavailable or a notification fails after commit. They request an authorized deadline check when the server reports the countdown has expired. Both operations use the same settlement rules. A room with both players disconnected can settle its overdue round when someone returns.
- Abandon an unstarted lobby after 30 minutes and an active room after one hour without a committed action. Keep completed results for 24 hours. Deny reads and writes once the relevant TTL expires. Use the daily authenticated cleanup function for bounded deletion batches. Votes have their own shorter deadline. No account data or telemetry is required for this release.

## Deploy and verify

1. Sign in to Vercel and link a target project. On a dedicated Neon database or branch, run [001_rooms.sql](../server/online/migrations/001_rooms.sql) through the Neon SQL editor or `psql` using a migration role. Give the runtime role read and write access to the three `draft_` tables and use its pooled Neon URL as `DATABASE_URL`.
2. Set `ONLINE_ORIGIN` to the exact intended preview or production origin, such as `https://draft.example.com`, with no trailing slash. Set `ONLINE_SESSION_PEPPER` to an independently generated random secret of at least 32 bytes. Use different values and a separate database for preview and production. Configure these values in Vercel’s project settings and keep them out of frontend builds.
3. Create a Pusher Channels app, enable authorized connections and TLS, and leave client events disabled. Set the four `PUSHER_` values from the app settings. The polling fallback supports preview testing before the Pusher credentials are configured.
4. For daily physical cleanup, configure `CRON_SECRET` and a scheduled `GET /api/online?cleanup=1` with `Authorization: Bearer <CRON_SECRET>`. Every room access already enforces expiry. The cleanup endpoint deletes up to 500 rooms and 5,000 old rate buckets per run.
5. Run `npx vercel deploy` and test the preview in two browser profiles. Create a room from **Play Online**, open the invite, refresh the join page, and join. Start a match and submit bids from both devices. Reload one device before the second bid, then finish and vote. Verify the browser establishes a private Pusher subscription, that it recovers with polling if the subscription drops, and that the signed cleanup route works before running `npx vercel deploy --prod`.

The automated checks use `npm run test` and `npm run test:e2e`. They run the same schema and HTTP handlers on an embedded PostgreSQL database and cover join races, replay, write rollback, sealed bids, timeout, reconnect, voting, and the complete local and online browser journeys. Hosted Neon and Pusher checks need the live provider accounts above.
